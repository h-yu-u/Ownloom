# 贡献与评审

[文档入口](README.md) · [开发指南](development.md) · [编码规范](code-standards.md)

欢迎可复现的问题报告与聚焦的 Pull Request。较大的产品行为、依赖、协议或架构变化先在 issue/PR 中说明目标和取舍；文档不能把尚未采纳的方案写成当前能力。

## 提交问题

通过 [GitHub Issues](https://github.com/h-yu-u/MlxDesktop/issues) 提供系统与芯片、源码提交/应用版本、模型来源与 revision、复现步骤、期望行为、实际行为及脱敏错误信息。不要上传密钥、个人会话、模型权重或完整私人诊断。

安全问题不要在公开 issue 中粘贴可用秘密或私人数据。优先使用仓库 Security 页提供的私密报告入口；如未启用，先向维护者请求私密联系渠道，再提供敏感复现材料。

## 准备变更

1. 阅读 [AGENTS.md](../AGENTS.md)、[架构](architecture.md)、编码规范、[经验记录](../LESSONS.md)及所属子系统参考。
2. 从当前主线建立独立分支；存在并行工作时使用自己的 worktree，不切换、清理或提交其他会话的工作区。
3. 只实现当前目标。跟踪入口、调用者、状态、持久化和错误路径；保留用户配置与兼容性约束。
4. 根据[子系统维护规则](subsystems/README.md)更新所属参考。用户承诺变化时同步英中 README，开发命令变化时同步开发指南。
5. 运行适用检查，记录环境、结果和未运行项；不要将测试数据或本机输出提交到仓库。

## PR 说明

每个 PR 的正文至少包含以下内容，可按影响范围精简：

| 项目       | 要回答的问题                                                         |
| ---------- | -------------------------------------------------------------------- |
| 问题与目标 | 哪种场景受影响，为什么需要修改？                                     |
| 语义变化   | 在什么触发条件下，用户或调用者看到的行为如何变化？哪些契约保持不变？ |
| 所属文档   | 受影响的子系统、长期规范或用户说明在哪里？                           |
| 验证       | 用什么命令，在什么环境/提交上得到什么结果？修复前哪个行为测试失败？  |
| 限制       | 哪些平台、真实模型、外部服务或发布环节未验证？                       |
| 兼容与依赖 | 是否涉及数据迁移、配置、协议、默认值、包版本或分发内容？             |

提交说明应描述具体行为，并在正文保留主要验证结果。大变更不能仅留一个笼统标题。提交后检查 `git show --stat HEAD`，确认只有属于本任务的文件。

## 评审与合并

评审者沿实际运行路径检查基线与 head，核对状态所有者、失败语义、同类调用者、文档链接和证据范围。行为修复的回归应能检测所修复问题；生成器或门禁变化需要有能发现错误的检查。

文档 PR 也应核对示例命令、源码路径、限额及英中承诺。已有测试失败、检查缺失、仅编译未运行和 FakeEngine 范围要明确记录，不能用“主线也这样”隐藏风险。

合并由维护者决定。评审记录应绑定明确 head；head 变化后，重新核对受影响的差异与检查。合并、打标签和发布是不同动作，文档合并本身不代表应用可正式分发。发布步骤见[发布验收](release-acceptance.md)。

## 许可证与第三方内容

提交者应确认有权贡献代码、文档、图标或测试素材。保留复制或分发内容要求的版权和许可说明，说明外部代码/素材来源。项目采用 [MIT License](../LICENSE)；第三方包、模型权重和外部服务仍遵循各自条件。

构建包包含 Runtime、Node/Pi 和可选推理依赖，维护者需要核对实际分发内容与所需 notices。不能用根许可证替代第三方许可，也不能把仅作架构参考的项目描述为已经嵌入的依赖。
