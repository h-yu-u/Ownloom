## 维护一份参考

职责、接口、状态转移、运行路径、兼容规则或失败行为改变时，在同一 PR 更新所属参考。保持契约的内部重构无需为了产生文档 diff 而改写说明。

一个事实只维护在一个所属页面。跨子系统语义通过链接连接，避免复制限制表、测试数量和实现清单。引用源码文件及命名符号；解释代码签名没有表达的字段含义、约束和失败语义。新增页面必须从本索引可达。

每份参考应包含：

1. **职责与边界**：提供什么行为，谁拥有资源与状态，和哪些子系统交接。
2. **事实来源**：入口、应用服务、领域规则、持久化及测试的源码链接。
3. **主要运行路径**：请求从接纳到可观察结果的过程，而非逐个函数罗列。
4. **状态与失败行为**：取消、重试、重启、晚到事件、部分成功及持久化语义。
5. **约束与兼容性**：安全边界、可变限额的来源、兼容前提和当前限制。
6. **验证入口**：确实存在的命令和能验证该保证的测试；实际结果链接验证记录。

现状与提案分开。提案放 issue/PR；被采纳的长期决策记录理由和代价，规范描述其约束，子系统记录其当前实现。未执行检查明确写未执行；不要在每篇参考追加开发日志。

## 描述语义变化

PR 按受影响子系统说明触发条件及可观察的前后行为。涉及接口、状态、兼容性或失败处理时逐项说明，链接维护参考、实现和验证证据。保持行为的重构应明确写明保持的契约及验证方法。

例如，修改下载恢复时，应说明应用退出前处于哪些状态、重新启动后进入什么状态、什么操作重新接纳任务，以及哪项测试覆盖这一变化。文档是作者对行为的说明，评审需要对照实现验证。

## 审查变化

1. 确认所属子系统、真正执行的路径和资源所有者。
2. 对比基线和修改后的实现，跟踪调用者、状态与副作用，不只看变更行。
3. 检查改变的契约是否已更新在所属参考，源码链接是否仍可达。
4. 确认测试或运行证据覆盖所声称的行为，明确未执行项。

文档检查不能证明产品行为。涉及运行时契约的改动仍需相应测试和实际环境验证。
